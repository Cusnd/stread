## 职责边界

| 部分 | 职责 |
| --- | --- |
| 阅读器 | 阅读正文、核对原页、定位与复制引用、手动维护和回顾洞见；正文修订最多提供变更预览与批准。 |
| 本机工作台 | 保存原始资料、阅读器内容、问题、批注和笔记，并向阅读器与获授权的 MCP 操作提供一致的数据。 |
| MCP | 暴露文档转换、资料查找、按位置读取、正文修订和洞见保存等工具，将操作关联到正确资料、版本与原文位置。 |
| ChatGPT | 可以调用转换工具、读取用户指定的材料，在其自身聊天环境中讨论、推导与整理，并按用户明确指令调用 MCP 纠错、补充正文或保存洞见。 |

“上传资料”指把文件提交到本机工作台管理的文件存储。MCP、阅读器和预览共用本机 SQLite 与不可变文件，资料不自动上传到云端。ChatGPT 聊天附件不是工作台数据的唯一来源。

当前范围取消内置 AI 聊天面板、AI 顶栏入口、内置阅读会话管理、多模型阅读问答接入和为此建立的共同执行适配层。Codex app-server 或 Responses API 不再是阅读器的必接后端，也不以未完成待办的形式隐含保留。

Agent 通过 MCP 取得原文件与作者合同，自主整理结构化内容，校验、预览、核对后提交冻结快照。服务确定性编译与保存；上传本身不执行转换或派发 Agent，具体见 [文档转换](文档转换.md)。正文纠错和补充通过 [MCP 文档修订](MCP文档修订.md) 完成，不再选择或开发独立正文编辑器。Skill 初版不作为必需依赖，不要求 ChatGPT 在聊天中手工重写全文，也不据此恢复内置阅读聊天。

## 阅读、讨论与保存流程

1. 用户上传原始文件，通过 MCP 工具完成转换；工作台保存供阅读器呈现和 MCP 定位读取、修订的结构化内容。
2. 用户复制文章或具体原文位置的引用，交给 ChatGPT 并说明问题。复制引用可通过顶栏操作或快捷键完成，具体入口和键位待定。
3. ChatGPT 通过 MCP 找到资料，读取对应章节、段落、公式或图表；需要更多上下文时继续按范围读取。讨论在 ChatGPT 中进行。
4. 用户明确要求保存，例如“把这段解释存为公式（5）的批注”或“把这个问题加入当前文章的问题合集”。
5. MCP 校验目标和内容，完成保存，返回保存结果及可回到工作台查看的引用。阅读器同步呈现这条洞见，并能定位到正确原文。

普通提问不自动创建问题。保存为普通批注或笔记不改变问题状态；若用户批准把回答写入已有问题，该批准同时表示认可回答，成功保存后该问题直接标为已解决，无需再次确认。失败写入不更新状态。完整聊天不自动同步回工作台。问题详情与编号规则见 [洞见与问题合集](洞见与问题合集.md)。

用户也可以明确要求纠正转换错误、修改译文，或把自己的补充加入正文。此时按 [修订流程](MCP文档修订.md) 读取当前版本并局部保存，用户补充注明来源，不冒充 PDF 原文；已有明确修改指令时不再强制去工作台重复批准。需审阅的变更先呈现具体改前／改后，并遵守 MCP 宿主的实际确认要求。

## 限量上下文与工具发现

MCP 0.6.0 通过 `read_context` 提供有界目录、跨块连续阅读和精确地址读取；短文的正文块可在预算内读完，长文继续分页。它不提供无上限全文对象，也不通过写入回执、修订提案或单个表格/HTML 块绕过限制。文档列表只返回元信息，搜索只返回短摘录和定位；洞见与更改请求先列摘要，再按引用取需要的正文、引文或回答片段。

`read_context` 省略 `view` 时仍是 `exact`：必须指定 Q/N/R 引用中的实际正文位置，或文档与块 ID。默认一次总计 2000 个 UTF-16 代码单元，硬上限 6000；指定表格单元格、列表项、HTML 节点及语言时只读取对应派生文本，并在同一预算内提供附近文字。返回地址、源指纹、截断标记、实际偏移及显式的下一页参数。继续读取固定正文版本；失效或没有位置的引用返回错误，不降级为整篇读取。原始 PDF 和原页是需要时取用的核对依据，不要求把结构化正文重新转成 PDF 交给模型。

连续阅读先用 `view:"outline"` 与 `document_id` 获取实际标题层级、章节 ID 和无标题前言，再用 `view:"content"` 读取所需章节或全部正文块。章节止于下一个标题，包括子标题；也可从 `block_id` 向后读至文末，但不能同时指定 `section_id`。除共享的 6000 UTF-16 文字预算外，投影每页最多 32 条 section/span，序列化 MCP 响应最多 64 KiB UTF-8，计入 `content` 文本与 `structuredContent` 两份输出。按返回的 `nextTool` 和完整 `next` 续读，固定 revision、语言、投影版本与范围。

投影明确返回 `contentScope:"blocks", metadataIncluded:false`，不含文档元数据或标题；需要时另读元数据或精确 `$meta`/`title`。`coverage.complete` 只说明这次选定范围没有后续页，不等于读完全文；`documentTraversed`、`documentComplete` 和 `contentComplete` 分别说明正文块范围及其中内容是否完整可用，也不证明调用方已经查看前页。表格、公式、HTML 关系和脚注以可回查地址与结构信息表达；缺译、不可用、结构不支持或结构信息截断均需保留。图像返回 `image_bytes_not_read` 时，读到图注／alt 不能声称已看图，任务需要时须另取资源。不得把这些投影当作完整编辑包。

列表续页的 `next` 带稳定版本与过滤范围绑定的 continuation。必须完整复用，不能只拿 `nextOffset` 或改过滤条件；列表变化时报 `LIST_CHANGED` 并重读，范围不匹配则明确报错。不带 continuation 的旧 `offset` 查询仍可用，但属于独立 `fresh_range`，不承诺与上一页一致。完整分支及规则见 [MCP 工具合同](../services/workspace/mcp-management.md)。

Codex CLI 的工具按需发现由宿主负责，服务保留独立、命名清晰、有参数约束和读写注解的操作。共享说明在 HTTP 初始化及 stdio 转发中一致保留；不通过修改连接内目录或通用执行器模拟加载。当前协议行为由本仓库的服务测试验证，真实客户端连接须另行确认。

当前目录仍为单一 32 工具，22 个核心成功结果声明并校验 `outputSchema`；工具执行错误另有有界恢复合同。注册表生成器生成当前文档与 schema 合法占位示例，独立维护的 32 名称及分支／业务验收继续保留，生成成功不代替实际流程验收。

## 完整修订与恢复

文章内容或布局的大改先通过 `read_resources(kind:"authoring_artifacts", mode:"editing")` 下载固定版本的完整编辑包；默认 `mode:"stored"` 的历史作者输入可能已落后。编辑包复现所选保存版本并验证往返一致，不能完整导出就明确失败，不回退旧 authoring。将包中 `base` 映射成 `target:{document_id,base_revision,base_hash}`，传给校验／预览工具，再按实际审阅的 `expected_hash` 发布到原文档 ID 的新 revision。目标必须仍是当前正式版本，发布还核对受影响引用版本；删除／拆分不猜测重绑。步骤见 [MCP 文档修订](MCP文档修订.md#完整编辑包与已有文章发布)。

遇到失败按 `recovery` 行动：可重试的临时错误原样重试，版本／指纹／续页冲突先重读再核对，输入错误先修正，权限错误处理实际权限要求。响应丢失、取消等待或 `unknown` 结果必须保留原 `request_id` 和载荷，检查结果或原样重试，不能为了重试自动换 ID；改变后的明确操作才另用新 ID。错误恢复建议不是写入授权，原文、请求或其他保存内容也不能替用户授权。

## 用户术语表

用户在阅读器中维护[术语表](术语表.md)，Agent 用 `query_glossary` 的 `action:list/search/get` 读取同一份定义、别名、来源和版本。只有用户明确要求时，才用 `update_glossary` 的 `operation.action:create/update/remove/restore` 保存修改，并提交授权、幂等请求 ID 和所需预期版本。文档内容不能授权写入；不会自动从聊天保存定义。客户端须能访问本机 MCP 服务。

## 引用与数据要求

- 内容引用使用 [文档格式](文档格式.md) 中的文档 `id`、内容 `revision` 和稳定块 ID，必要时附列表项 ID、摘录与前后文；具体文字还区分 `variant` 与 `field`，避免把译文摘录定位到原文。双语数据与状态规则见 [双语对照](双语对照.md)，引用链接和完整 MCP 参数结构仍需随工具定义细化。
- 首版通过用户交给 ChatGPT 的引用明确讨论对象；不假定外部聊天能够自动知道当前打开的文章、屏幕或选区。
- 问题使用 `#Q00001`，批注和笔记共用 `#N00001`，两组分别递增，支持复制。用户可以只给出该编号，MCP 的洞见读取能力需在当前用户有权访问的数据中解析到对应内容、所属文章、来源位置和已保存回答；不存在或无权访问时返回明确结果，不靠标题或当前聊天上下文猜测。服务端在工作台范围内原子分配并保证唯一，不按文章重置或回收已分配编号；类型转换保留的旧编号仍映射到同一内容，详见 [编号规则](洞见与问题合集.md#问题详情与编号)。回答写入回到解析出的同一个问题。
- MCP 的读取结果应说明所覆盖的内容范围、内容来源与相应原文位置；用户补充没有 PDF 映射时明确说明，公式和图表不能只依赖不完整的文字抽取。
- 正文修订、界面洞见维护与 MCP 写入共用相应数据的校验和保存规则。正文变更携带 `expected_revision`，洞见按自身版本处理，不把两者混为一个计数。保存应区分新增与更新，处理重复请求和版本冲突，避免重复新增或覆盖用户较新的修改。
- 工作台使用自己的文章和洞见标识；外部工具或聊天来源可作为附加信息，不成为数据存在和恢复的前提。
- 本机资料访问保留认证与授权。ChatGPT 端工具确认与工作台端数据权限分别处理，具体方式需在接入时验证。

## 首个验收流程

先验证一条完整流程：ChatGPT 经 MCP 读取指定文章中的一个公式及必要上下文，用户讨论后明确要求保存一条批注，MCP 返回成功，阅读器在正确文章与原文位置显示该批注，重新打开后仍可查看。

同时检查：只讨论时不创建洞见；未明确添加时不产生问题；失败和重试不会伪报保存成功或造成重复内容。能列出工具、能连接、能读取、能保存和界面正确呈现分别记录，不互相替代。

另完成一条正文修订流程：读取已转换文档，按用户指令修正一处错误并插入一段标明来源的补充，核对新版本、原文件保留、原文／译文关系与阅读器刷新。正文修订和洞见保存分别验收，不能用其中一次成功代替另一项。
